# 08 — Post every verdict the moment it is reached

Status: ready-for-agent

**Blocked by:** None — can start immediately.

**What to build:** an adjudication that dies part-way has posted everything it decided. In an observed run the
adjudicator ran 256.5 minutes and died with **0 of 89** verdicts posted — confirmed on the forge as 89 threads with no
replies — discarding 535,499 billable tokens and 4h16m; its re-dispatch posted as it went and finished the same 89 in
about 33 minutes. Nothing in the agent's contract asked for either behaviour. Settled as D15 and D16 in `../spec.md`.

- [ ] `assumption-reviewer` posts each **verdict** before beginning the next **assumption**'s legwork. Step 4 becomes
      two beats: the whole-set read, then a per-assumption loop — legwork, reply, next.
- [ ] The instruction constrains **when** a verdict is posted, not how many replies an assumption gets. Step 4 already
      says "reply with exactly one verdict", so a sentence in that register restates what the file has and leaves the
      batching untouched.
- [ ] Reading the whole set first is unchanged, and the reason is still stated: it is what makes a conflict between two
      assumptions available as **grounds**. The set is every assumption on the **change request**, those already
      carrying verdicts included — not only the ones this **dispatch** will adjudicate.
- [ ] A clause where the verdict is posted says why posting as it goes is safe rather than merely faster: the reply is
      the durable, idempotent mark **Resume** already filters on. It points at that paragraph rather than restating the
      fact, which the file carries twice already.
- [ ] A verdict already posted is corrected by a further reply when later legwork overturns it. The newest verdict
      reply on an assumption is the one that stands, and the correction leaves the resolution state the new verdict
      calls for.
- [ ] **Verdicts** carries that rule; **Comment channels** gains the operation it needs — GitHub's
      `unresolveReviewThread`, GitLab's `resolved=false` — because an `accept` resolves its comment and an `override`
      correcting it must not stay resolved.
- [ ] The issue-comments projection gains `created_at`. It is the one channel with no threading, and without a
      timestamp a correction cannot be told from the verdict it corrects. It stays a small projection, so the
      truncation reasoning below it is untouched.
- [ ] A dispatch corrects only verdicts it posted itself. One already carrying a reply when the dispatch began is done,
      per **Resume**; where it conflicts with a verdict being reached now, the conflict goes in the new verdict's
      **grounds**.
- [ ] Nothing splits the set across dispatches or caps how many assumptions one dispatch takes.
- [ ] What it reports is unchanged — the count of each verdict kind, and every **escalation** one line each. A
      corrected verdict counts once, as the verdict that stands.
- [ ] Register and the file's column width are matched: it wraps at 120 characters throughout, with no line over.

**Triage, 2026-08-23 — stays `ready-for-agent`; five criteria added, and the original six sharpened.**

The claim holds, and it is worth being precise about why, because the sentence looks like it already says the right
thing. `plugin/agents/assumption-reviewer.md:34` reads *"**Adjudicate them one at a time**, giving the last one the same
scrutiny as the first: read the whole set first … then do the legwork below and reply with exactly one verdict."* Both
"one at a time" and "exactly one verdict" constrain **shape** — one verdict per assumption, never two — and neither
constrains **timing**. Read-all, legwork-all, reply-all satisfies that sentence exactly, which is what the observed run
did. Every figure in the ticket checks out against `../spec.md` lines 41-43, and line 421 records the forge confirmation
as itself verified. Nothing in `plugin/` instructs incremental posting anywhere, and no other ticket in this set touches
this file, so there is nothing to sequence against.

**A near-miss phrase next door is the most likely way to land this ticket without fixing the bug.**
`change-request-creator.md:44` already says *"Post one comment per entry that has none — one comment per entry, never a
batch"*. An implementer looking for the house register will find it, and it is about shape, not timing: copied across,
it writes something `assumption-reviewer` already says and leaves the 89-verdict batch exactly where it was. The second
criterion now names that trap rather than trusting the first one to be read carefully.

**Incremental posting breaks "the whole set", on your call.** Step 3 collects only assumptions carrying no verdict
reply, and step 4 closes with "done when every assumption *from step 3* carries a verdict reply" — so "the whole set" is
step 3's collection. That was harmless while a dispatch either did all 89 or, as observed, posted none. This ticket
makes partial completion the normal case, and then a resumed dispatch reads only its own leftovers, forfeits conflict
detection against everything already adjudicated, and makes step 4's claim to be "the only agent that sees every fork
against the finished branch" false precisely when the conflict ground matters. The third criterion now names the set
independently of step 3.

**Posting as you go can be overtaken, and the contract had nowhere to put that.** Reading the whole set first makes a
conflict *visible* before the first verdict — that is why D15 keeps it — but reading is not legwork, and assumption
60's legwork against the code can overturn verdict 3, which is already posted. Under batching you revised before
posting; now you cannot. Settled on your call as a correcting reply: newest stands, which is what line 94's `last:100`
already rests on when it justifies itself as *"an assumption's verdict reply is a thread's newest comment and never its
oldest"*. Two mechanical gaps follow, and both are criteria now.

- **No unresolve operation exists anywhere in the plugin.** An `accept` resolves its comment; correcting it to
  `override`, whose whole contract is that the comment stays unresolved for a fix wave to find, has to reverse that.
  Both forge blocks give worked commands for every other operation, so this one is added rather than left as the single
  guess in the file.
- **The issue-comments channel cannot order its replies.** Its `--jq` projects `{id, login, body}`, no timestamp, and it
  is the one channel with no threading — so it is exactly where "newest stands" has nothing to read. `created_at` is
  added; the projection stays small, so the paragraph below it explaining why the filter is not tidying still holds.

**The correction stops at the dispatch boundary, on your call.** A dispatch corrects only verdicts it posted itself. The
filter "carries a reply is done" is what makes re-entry cheap and terminating, and it is the same property D15's safety
argument rests on; a dispatch that may revisit its predecessor's verdicts has no fixed point. Nothing is lost — where
dispatch 2's reading of all 89 turns up a conflict with a verdict dispatch 1 posted, that conflict is grounds for the
verdict being reached now, which is where a fix wave reads it.

**Two things deliberately left alone.** The report is genuinely unchanged: a corrected verdict counts once, as the one
that stands, so "how many verdicts of each kind" still describes what the change request carries. And
`change-request-creator` posts 89 comments under the same death risk and could take the same timing rule — out of scope
here on your call, so it is recorded rather than actioned. No ADR: a contract sentence is trivially reversible, and D15
and D16 already carry the decision. No glossary work either — the one candidate, `legwork`, was bolded in D16 as though
it were a term, has no `CONTEXT.md` entry, and names a section of one agent's contract rather than a concept the domain
turns on. D16 is unbolded to match this ticket and the agent file; `CONTEXT.md` is untouched.
