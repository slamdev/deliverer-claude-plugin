# 03 — Report why a round failed, in one word a caller can act on

Status: ready-for-agent

**Blocked by:** None — can start immediately.

**What to build:** a round that died reports why in one machine-readable word, and a result the harness marked
successful while saying it failed is reported as the failed round it was rather than as a completed one. An observed run
had two rounds report their status as completed while carrying `API Error: Connection closed mid-response` and
`Prompt is too long` where reviewer prose belongs, so the only way to learn they were dead was to query the forge for
comments that never came. Settled as D5, D6 and D22 in `../spec.md`.

- [ ] A terminal failure's reason begins with one of a closed vocabulary: `prompt_too_long`, `deadline_exceeded`,
      `connection_lost`, `not_logged_in`, `no_result`, `backend_error`.
- [ ] **Every** terminal failure the server can produce carries one, not only the ones the message-to-event narrowing
      returns: a round aborted on its bound, a backend that could not start it, a run whose stream ended with no
      result message, and a failure the backend reported itself.
- [ ] Both bounds end on `deadline_exceeded`, and the reason text says which one ended the round — the idle timeout
      ticket 04 adds takes no seventh word.
- [ ] The vocabulary is documented where a caller reads it, on the status tool.
- [ ] That documentation says the code rides on a **failed** round. A cancellation's reason carries none, so a caller
      is not sent looking for a word that is not there.
- [ ] No key is added to the published payload — the code rides on the one-line reason that is already there.
- [ ] A successful result whose prose *begins* with the harness's own error text becomes a failed event carrying the
      matching code, and the anchoring is commented: a review whose findings discuss a dropped connection must not
      fail its own round.
- [ ] The strings that match are the two the observed run carried: prose opening `API Error: Connection closed
      mid-response` becomes `connection_lost`, and prose opening `Prompt is too long` becomes `prompt_too_long`. One
      leads with `API Error:` and the other does not, so each anchor matches the harness's own text rather than a
      tidied form of it.
- [ ] A successful result whose prose merely mentions an API error stays `completed`.
- [ ] The not-logged-in case keeps its existing message and gains its code.
- [ ] A failed round still carries what it **spent**.
- [ ] ADR-0010 says a result the harness marked successful while saying it failed is not a completed review, however
      the SDK classified it.
- [ ] The amendment says what changed and why, because a decision changes in the one place it lives.
- [ ] The narrowing is checked at its existing seam — a throwaway script feeding it hand-written result messages, run
      by hand and not committed — and the codes that seam cannot reach, the bound's abort above all, are driven the
      same way at the lifecycle's own injection point, plus the scripted-backend lifecycle, `typecheck` and `lint`.

**Triage, 2026-08-23 — stays `ready-for-agent`; four criteria added, one widened.**

The claim holds at the code path. The message-to-event narrowing returns `completed` for every `success` result whose
prose does not match its one anchored pattern, the not-logged-in one, and nothing else reads that prose — so a result
carrying the harness's own error text publishes as a completed round with that text where the review belongs, which is
rounds 1 and 2 of the observed run. Nothing here is already built: none of the six words appears anywhere in `plugin/`,
in the ADRs or in `CONTEXT.md`. The mechanism the change rides on does exist — `reason` is already one of the nine
published keys, already carries the failure message, and `code-reviewer` is already told to report it verbatim, so a
prefixed code reaches the orchestrator with no change to that agent. No prior rejection of this shape is on record; the
repository keeps no `.out-of-scope/`.

Four defects in the criteria, now fixed:

- **Two of the six words were unreachable from the only seam the checks named.** The server has six places that emit a
  terminal failure: two in the narrowing, two in the agent backend's run loop, and two in the review lifecycle. A
  `deadline_exceeded` can only come from the bound's abort, which is neither — so an implementer working at the named
  seam would have shipped a closed vocabulary whose word for the failure that killed **half** the observed run is never
  emitted, with every box ticked. A box now covers every site, and the verification box reaches the ones the seam
  cannot.
- **A cancellation was left holding an unlabelled reason.** That key is published for a failed *and* a cancelled round,
  and the status tool's own text for it says so. None of the six words is a cancellation, so "the reason begins with
  one of these" invites either a seventh word — against a closed vocabulary — or documentation that lies to a caller
  reading the first word. The documentation box now says the code rides on a failed round.
- **The two bounds of ticket 04 had no stated code.** D8 keeps the idle bound in the reason text rather than a second
  key, so both bounds end on `deadline_exceeded` with the prose distinguishing them; unstated, `idle_timeout` is the
  obvious invention. Said here, because this is also the one sentence 03 and 04 both rewrite: whichever lands second
  keeps the other's clause.
- **"The harness's own error text" did not say which text.** The two observed strings differ in shape — one leads with
  `API Error:` and one does not — which is exactly what an anchored match gets wrong, and a pattern anchored to a
  tidied form would leave the defect shipping under a green box. Both strings and their codes are now named.

No glossary work: D23 settled that, and the payload's `reason` is why a round ended, not the evidence sense that
`CONTEXT.md` gives to **grounds**.
