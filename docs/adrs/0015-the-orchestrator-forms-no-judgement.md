# The orchestrator forms no judgement and dispatches paths, not contents

The agent that runs an **epic** reads it, **dispatches** every stage, keeps the task list and **reports**. It is
read-only. It never forms a view on a **review finding**, on a design, or on whether the work is good, and what it does
with a stage that went wrong is put it back to an agent or report it — never fix it. A mechanical question about the
tree **or the forge** is its own to settle — does it build, does this symbol exist, what does the branch carry, are the
change request's **checks** green — because that asks whether a report's fact is true rather than whether its judgement
is right. The two are one exception and not two: whether a check is green is as mechanical as whether the tree builds,
and reading it is the same move as reading the branch.

Each dispatch carries paths rather than the contents behind them, so the dispatched agent opens the document for itself
and meets the repository first-hand. What a dispatch names in its report is the whole of what the orchestrator knows,
and what a report leaves out is invisible to it — which is why a report that leaves it unsure is answered by
re-dispatching the stage rather than by going to look.

Putting a stage back is one move however it is made: continuing a dispatch that still holds the stage's context and
dispatching a cold one differ in cost, not in kind. The sequencing is what differs. A dispatch that acknowledges the
work and finishes it in the background has not **reported**, and a stage whose report has not arrived has not finished —
so the stage that reads it waits on that report, and never on a duration the orchestrator picked.
